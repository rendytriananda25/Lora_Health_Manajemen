1. Konsep Dasar (Clean Architecture)

🐒 Analogi Monyet (Penjelasan Super Gampang)

Bayangkan aplikasi kita adalah sebuah Hutan Restoran. Di arsitektur jadul (berantakan), kalau si Monyet (User) lapar, dia harus lari sendiri manjat pohon pisang (Firebase), metik sendiri, ngupas sendiri, baru makan. Kalau pohonnya tinggi, monyetnya jatuh (Aplikasi Crash).

Di Clean Architecture, kita bikin tim restoran yang profesional:

  • UI / Page (Meja Makan): Tempat Monyet duduk manis. Monyet cuma tau pencet bel "Minta Pisang". (UI tidak ada kode database sama sekali).
  • Provider (Pelayan): Pelayan yang nerima pesanan. Dia suruh monyet nunggu (Loading Screen). Kalau pisang datang, dia taruh di meja.
  • UseCase (Koki): Tukang olah spesifik. Ada koki khusus "Kupas Pisang", ada koki khusus "Bikin Jus". (Satu file = Satu tugas).
  • Repository (Mandor): Yang ngecek kualitas. Kalau pisang busuk (No Internet), Mandor ngasih tau Koki: "Gagal nih!". Mandor pakai aturan khusus (Result<T>) biar restoran nggak kebakaran kalau ada error.
  • DataSource (Tukang Panjat): Tugasnya murni cuma interaksi sama Pohon Pisang (Firebase / Database).
👨‍🏫 Bahasa Teknis (Jawaban untuk Dosen)

Aplikasi Lora-1 mengimplementasikan Clean Architecture dengan pemisahan Separation of Concerns (SoC) yang sangat ketat menggunakan Provider Pattern untuk State Management. Alur datanya bersifat satu arah (Unidirectional Data Flow): UI → Provider → UseCase → Repository → DataSource. Hal ini mempermudah unit testing dan mencegah memory leak karena presentation layer sama sekali tidak diizinkan menyentuh Firebase SDK secara langsung.

2. Modul Workout (Program Latihan Acak)

🐒 Analogi Monyet

Kenapa monyet A dan monyet B dikasih jadwal olahraga yang beda tiap hari padahal levelnya sama? Karena sistem ngegabungin KTP si Monyet sama Kalender hari ini buat ngocok arisan gerakan olahraga. Jadi tiap monyet dapet urutan gerakan yang unik terus tiap hari!

👨‍🏫 Bahasa Teknis (Jawaban untuk Dosen)

Logika daily routine generation berada di WorkoutData.generateRoutine(). Sistem melakukan Hashing terhadap variabel unik User UID ditambah dengan dayOfYear (Hari ke-sekian dalam tahun ini) untuk dijadikan parameter Random(seed). Pendekatan ini menghasilkan pengacakan yang deterministik dan unik per-akun, memastikan dua pengguna berbeda tidak akan mendapatkan sekuens gerakan yang identik meskipun level mereka sama. Data gerakannya ditarik dari _onlineWorkoutData (Firebase) agar dinamis, atau mundur ke data statis lokal jika offline.

3. Modul BMI (Kalkulator & Grafik Berat Tubuh)

🐒 Analogi Monyet

Monyet nimbang berat badan. Datanya dicatat sama Pelayan, dikasih ke Koki, terus Tukang Panjat nyimpen catatan itu di pohon (Firebase). Hebatnya, begitu catatannya nempel di pohon, Pelayan otomatis teriak ke meja: "Woi data baru nih!", dan grafik di meja otomatis berubah tanpa si Monyet harus pencet refresh.

👨‍🏫 Bahasa Teknis (Jawaban untuk Dosen)

Modul BMI menggunakan pendekatan Reactivity. BmiProvider memanggil UseCase SaveBmiHistory. Setelah proses penyimpanan ke Firebase Realtime Database mengembalikan nilai Success (Right), Provider secara otomatis mengeksekusi FetchBmiHistory dan men-trigger notifyListeners(). Karena komponen Bar Chart dibungkus dengan Consumer<BmiProvider>, grafik tren berat badan akan me-render ulang seketika secara real-time merespon pembaruan data.

5. Modul Settings (Profil & Fungsi Admin)

🐒 Analogi Monyet

Monyet mau ganti foto profil. Dia ambil foto dari dompetnya (Storage lokal HP), terus ditempel pake lem di lokernya (SharedPreferences). Jadi gak usah capek-capek upload fotonya ke awan (Cloud).

👨‍🏫 Bahasa Teknis (Jawaban untuk Dosen)

Penyimpanan foto profil dikelola secara hybrid. UseCase SaveLocalPhoto akan menyimpan absolute path file gambar ke memori lokal HP menggunakan SharedPreferences (melalui SettingsLocalDataSource). Jika URL lokal ini tidak tersedia, aplikasi akan otomatis fallback memanggil photoURL bawaan akun Google dari Firebase Auth.

Fitur Rahasia (Admin Mode): Jika label "Lora Version 1.0.0" di tekan lama (Long Press), aplikasi memunculkan dialog admin yang memicu metode seedToFirebase(). Fungsi ini akan menulis paksa data Master JSON Lokal (seperti data Makanan dan Gerakan) langsung ke Firebase Realtime Database. Pendekatan ini adalah inovasi Content Management instan tanpa perlu repot merilis ulang APK ketika ada pembaruan materi olahraga.

6. Modul Gamification (Sistem Badge & Pangkat)

👨‍🏫 Bahasa Teknis (Jawaban untuk Dosen)

Sistem ini dirancang dengan pendekatan Lightweight Service, tidak diforsir menjadi Clean Architecture penuh karena tidak memiliki manipulasi data. BadgeService dan RankSystem bertugas memantau Total XP pengguna dari Firebase, membandingkannya dengan Threshold Array, lalu me-return Asset Image Path lencana yang terbuka. 7. Core Services (Notifikasi & Lokalisasi)

👨‍🏫 Bahasa Teknis (Jawaban untuk Dosen)
  • Multi-Bahasa (i18n): Menggunakan LanguageProvider yang membaca file JSON di direktori assets/lang/. Di UI cukup dipanggil via lang.translate('kunci').
  • Notifikasi Lokal: Memanfaatkan flutter_local_notifications dalam WorkoutReminderService. Algoritma penjadwalan beroperasi murni di level klien (client-side background task) sehingga menekan cost tanpa perlu konfigurasi Push Server Backend.
  • Theming System: Warna aplikasi menggunakan variabel dinamis dari ThemeProvider. Pemanggilan toggleTheme() mengganti tema dari Light ke Dark secara instan karena seluruh komponen terikat listener ke variabel tersebut.
